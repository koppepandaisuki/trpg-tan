# Stripe セキュリティ・チェックリスト対応状況

Stripe(決済代行/カード会社)から要求されたセキュリティ対策 6 項目への対応状況。
Stripe への回答時はこの文書をベースに使ってよい。

**前提: 当サービスは Stripe Checkout(ホスト型決済ページ)のみを使用しており、
カード番号等の決済情報をアプリのサーバー/ブラウザで直接扱うことは一切ない。**
入力フォーム(カード番号欄)は Stripe が自社ドメインでホストするため、EMV
3-D セキュア・カードデータの暗号化・PCI DSS のカードデータ保護要件は
Stripe 側の責任範囲であり、当方で別途実装する必要はない。

---

## 1. 管理者画面のアクセス制限と管理者の ID / PW 管理

| 要求事項 | 対応 |
|---|---|
| IP アドレス制限、できなければ Basic 認証等 | **対応済み**。Vercel Hobby プランには IP アローリスト(Firewall)機能が無いため、`/admin/*` に Basic 認証を設置(`middleware.ts`)。env `ADMIN_BASIC_AUTH_USER` / `ADMIN_BASIC_AUTH_PASS` の両方を設定して有効化(**要設定**)。 |
| 二段階認証/二要素認証 | **対応済み**。Supabase Auth 標準の TOTP(認証アプリ)を採用。管理者は `/admin/*` 閲覧に**必須**(未設定なら強制的に設定画面へ、設定済みでも毎セッション再認証)。`app/(app)/admin/layout.tsx` + `app/(app)/admin/mfa/*`。 |
| ログインフォームのアカウントロック(10 回以下で失敗) | **対応済み**。メール単位で失敗回数を追跡し、直近 30 分に 10 回失敗したらそれ以降のログイン試行を拒否(`lib/api/login-lockout.ts`)。成功時は即リセット。 |

## 2. データディレクトリ露出による設定不備対策

| 要求事項 | 対応 |
|---|---|
| 公開ディレクトリに重要ファイルを置かない | **元々満たしている**。Next.js の `public/` には画像 1 点のみ(`dice.png`)。`.env*` は `.gitignore` 済みでリポジトリにもデプロイ成果物にも含まれない。ソースコードや設定ファイルは Next.js のビルド成果物として配信されず、サーバーサイドのコードは実行環境内にのみ存在する(PaaS の性質上、ファイルシステムへの外部アクセス経路が無い)。 |
| アップロード可能な拡張子/ファイルの制限 | **元々満たしている**。全アップロード先(アバター/カバー/スクリーンショット/作品ファイル)は Content-Type の**許可リスト方式**(ホワイトリスト、拒否リストではない)。未知の MIME は拒否(`lib/format/upload.ts`)。 |

## 3. Web アプリケーションの脆弱性対策

| 要求事項 | 対応 |
|---|---|
| 定期的な脆弱性診断/ペネトレーションテスト | **運用課題**。`/code-review` や `/security-review` によるコードレビューは都度実施可能。外部診断ツールの定期実行は今回のスコープ外(必要なら別途相談)。 |
| SQL インジェクション対策 | **元々満たしている**。生 SQL の文字列結合は不使用。全て Supabase クライアント(パラメータ化クエリ)または PostgreSQL の `security definer` 関数(型付き引数)経由。 |
| クロスサイトスクリプティング対策 | **元々満たしている**。React の自動エスケープに加え、`dangerouslySetInnerHTML` は不使用(MFA の QR コードも data URI の `<img src>` で描画し、HTML 注入を避けている)。**今回追加**: CSP(Content-Security-Policy)、X-Frame-Options、X-Content-Type-Options 等のセキュリティヘッダを付与(`next.config.mjs`)。 |
| 最新のプラグイン/ソフトウェアバージョン | **今回追加**: CI(`.github/workflows/ci.yml`)で `pnpm audit` を実行し既知の依存脆弱性を継続的に検知。 |
| セキュアコーディング済みか、ソースコードレビュー(入力値チェック含む) | **元々満たしている**。全フォーム入力は zod でサーバー側再検証(クライアントの検証だけに依存しない)。 |

## 4. マルウェア対策としてのウイルス対策ソフトの導入、運用

**対象外(該当なし)。** 当サービスは Vercel(Web/API)+ Supabase(DB/Auth/Storage)の
フルマネージド PaaS 上で稼働しており、OS やファイルシステムを当方が直接管理する
サーバーは存在しない。ウイルス対策ソフトを導入・運用する対象(自社管理の
OS/ファイルシステム)が無いため、この項目は構成上該当しない。

代替の統制として:
- ユーザーがアップロードするファイルは実行されず、Supabase Storage に
  データとして保存されるのみ(コード実行経路が無い)。
- 依存パッケージの脆弱性は CI の `pnpm audit` で継続監視。
- 各 PaaS ベンダー(Vercel/Supabase)自身のインフラセキュリティ対策(SOC2 等)に
  基づいて運用されている。

## 5. 悪質な有効性確認、クレジットマスターへの対策

| 要求事項 | 対応 |
|---|---|
| 不審な IP アドレスからのアクセス制限 | 未実装(下記のレート制限で代替)。 |
| 同一アカウントからの入力制限 | **対応済み**。Checkout 作成系エンドポイント(作品購入 / ゴールドパック / 月額プラン)を全てユーザー単位でレート制限(20 回/分、`lib/api/rate-limit.ts`)。 |
| エラー内容の非表示 | **元々満たしている**。Stripe API のエラーは全てログにのみ記録し、利用者には「申し込み処理を開始できませんでした」等の汎用メッセージのみ返す(生の Stripe エラーを露出しない)。 |
| EMV 3-D セキュアや SMS 通知など本人確認 | **Stripe 側で対応済み**。Stripe Checkout は 3D セキュアを自動的に要求する(Radar のリスク判定に基づく)。当方は Stripe Checkout のみ使用しカード情報を扱わないため、3DS の実装責任は無い。**要設定**: Stripe ダッシュボードで Radar のルール(高リスク時 3DS 要求 等)を確認・有効化(`docs/stripe-operations.md`)。 |
| 有効性確認の回数制限 | **対応済み**(上記レート制限と同じ仕組み)。 |

補足: チャージバック(dispute)発生時は運営 Discord に即時アラートするフローを
追加済み(`docs/stripe-operations.md`)。

## 6. 不正ログイン対策(ユーザー登録、ログイン、アカウント変更)

| 要求事項 | 対応 |
|---|---|
| 不審な IP アドレスからのアクセス制限 **もしくは** 二段階認証/多要素認証 | **対応済み(2FA を選択)**。全ユーザーが `/account/settings` から任意で TOTP 二段階認証を有効化できる(`components/account/mfa-status-panel.tsx`)。加えてログイン失敗のアカウントロック(項目 1 参照)を全ユーザーのログインフォームに適用済み。管理者は 2FA が必須。 |

## 要ユーザー対応(env 設定・運用)

以下は本番運用開始前に必ず設定すること:

1. **Vercel 環境変数**:
   - `ADMIN_BASIC_AUTH_USER` / `ADMIN_BASIC_AUTH_PASS`(管理画面 Basic 認証、必須)
   - `CRON_SECRET`(異常検知 cron の認証)
2. **Supabase migration**: 0044〜0047 を本番に適用(未適用なら該当機能が動作しない)。
3. **Stripe ダッシュボード**: Radar ルールの確認、Connect 出金の遅延設定、
   webhook に `charge.dispute.created` / `charge.dispute.closed` を追加登録
   (`docs/stripe-operations.md` 参照)。
4. **管理者自身の 2FA 設定**: 初回ログイン後、自動的に `/admin/mfa/enroll` に
   誘導されるので、認証アプリ(Google Authenticator 等)で QR コードを読み取って設定する。
